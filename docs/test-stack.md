# Test stack

**Who reads this:** B setting up the test stack (the [`setup-teststack`](../skills/setup-teststack/SKILL.md) skill does it), C debugging a stack slot.

A reproducible Docker Compose deployment of the whole application. You put it into a known state from a **scenario file** that seeds the datastores directly. It is built for agents and automated tests: every command blocks until the stack is healthy and prints one JSON result line.

The engine is language neutral. It needs Node 20 and Docker (or a compatible engine through `TESTSTACK_DOCKER`) and nothing from the application's toolchain. Everything it knows about a codebase comes from two sections of the app repository's `.factory/config.json`: `stack` (compose file, host ports, URLs, how images are built) and `teststack` (datastores, readiness, scenarios). The `setup-teststack` skill (`skills/setup-teststack/SKILL.md`) walks an agent through creating both for a new codebase. `examples/eshop/` holds a complete setup for a .NET application.

## Quick start

```bash
factory teststack up                          # build images if sources changed, start, wait, load "default"
factory teststack load order-history          # clear everything and load another scenario
factory teststack reset                       # clear everything, base scenario only
npx playwright test -c playwright.teststack.config.ts
factory teststack down                        # remove containers and all data
```

`factory teststack` runs `scripts/teststack/teststack.mjs` of the factory install; `factory stack` runs `scripts/stack/slots.mjs`. Both find the app repository from the current folder (`git rev-parse --show-toplevel`), from `--root <dir>` or from `TESTSTACK_ROOT`.

## Files in the app repository

| Path | Content |
| --- | --- |
| `.factory/config.json` | The `stack` and `teststack` sections described below. |
| `.factory/stack/docker-compose.yaml` | The compose file (`stack.composeFile`). Written by hand, or generated by `stack.publish`. |
| `.factory/stack/scenarios/<name>/scenario.yaml` | Scenarios (`teststack.scenariosDir`). `_base` is loaded before every scenario. |
| `.factory/state/teststack/` | Generated state, git-ignored: the env file compose reads (`.env`), build stamps, and `slot-<n>/` for each slot. |

Machine-wide state (slot leases and the image build lock) lives in `~/.ai-app-factory/teststack/<project>/`, where `<project>` is `project.name` from the config, or the repository's folder name. Override the folder with `TESTSTACK_STATE_HOME`.

## Commands

| Command | Description |
| --- | --- |
| `up [--scenario <name\|path>] [--timeout s]` | Build if needed, `compose up -d`, wait, then load the scenario (default: `teststack.defaultScenario`). |
| `down` | `compose down -v`: removes containers and all data. |
| `build [--force]` | Build the images, only when needed. |
| `load <name\|path> [--hard] [--timeout s]` | Clear all state, then load the base scenario, the scenario's `extends` chain and the scenario itself. |
| `reset [--hard] [--timeout s]` | Same as `load` with only the base scenario. |
| `wait [--timeout s]` | Block until the stack is ready (default timeout: `teststack.timeoutSec`, 300). |
| `status` | One readiness pass, without waiting. |
| `validate [<name\|path>...]` | Parse and resolve scenarios (all by default). Needs no running stack. |
| `rebuild-changed --base <ref> [--services a,b]` | Rebuild only the images affected by `git diff <ref>...HEAD` plus uncommitted and untracked files, recreate only those containers if the stack is running, then wait. `--services` names services instead of (or on top of) a diff. |
| `services-for <files...>` | Print the compose services whose images those files affect (pure mapping, no Docker). |
| `publish [--check]` | Regenerate the compose file with `stack.publish`. `--check` fails on drift. |
| `drift` | (a pack command, `teststack.commands.drift`) Fails when the test stack no longer matches the application's own composition. The .NET pack runs `publish --check`: the compose file is generated from the Aspire AppHost (`stack.publish` = `node {packs}/dotnet/stack/aspire-publish.mjs --out {out}`: `aspire publish` with `TestStack=true` at the AppHost SDK's version, then the declared `stack.publishOverrides` of app.json, each with its reason). Because the AppHost is executed, conditional wiring, extension methods, callbacks, image tags and ports all count. An AppHost whose stack is not published from it fails; it never answers a plain ok. `factory init` drafts the publisher and makes drift an implement check; the CI gate runs it. |
| `logs [svc...]`, `compose <args>` | Run `docker compose` against the stack. These two pass the output through and print no JSON line. |

`--slot <n>` and `--root <dir>` go before the command. A repository or a language pack can add commands with `teststack.commands` (see [Extra commands](#extra-commands)).

**Output contract:** logs go to stderr, and stdout gets exactly one JSON line, for example:

```json
{"ok":true,"command":"load","scenario":"order-history","layers":["_base","default","order-history"],"mode":"soft","purgedMessages":0,"restarted":["api"],"elapsedMs":2140,"slot":0,"project":"shop-teststack","baseUrl":"http://localhost:18080","urls":{"web":"http://localhost:18080"},"webUrl":"http://localhost:18080","ports":{"web":18080,"db":18432}}
```

`up`, `load`, `reset`, `wait`, `status`, `build`, `down` and `rebuild-changed` carry the slot: `slot`, `project` (the compose project), `baseUrl`, `urls`, each URL again as `<name>Url`, and `ports`. When `ok` is false, the line also contains `error` and `exitCode`; `status` and `wait` failures list the checks that are not ready.

**Exit codes:**

| Code | Meaning |
| --- | --- |
| 0 | OK |
| 1 | Error |
| 2 | Not ready (timeout) |
| 3 | Invalid scenario |
| 64 | Usage or configuration error |

## The `stack` section

How the stack is built and addressed. Defaults are in `scripts/stack/config.json`; they name no port, service or command.

```json
{
  "stack": {
    "composeFile": ".factory/stack/docker-compose.yaml",
    "ports": {
      "web": { "base": 18080, "env": "WEB_HOST_PORT" },
      "db": { "base": 18432, "env": "DB_HOST_PORT" }
    },
    "urls": { "web": "http://localhost:{port:web}" },
    "baseUrl": "web",
    "env": { "DB_PASSWORD": "teststack-db" },
    "services": {
      "web": { "inputs": ["web/**", "shared/ui/"] },
      "api": { "inputs": ["services/api/", "shared/**/*.proto"] }
    },
    "rebuildAll": ["docker/", "package-lock.json"]
  }
}
```

| Key | Meaning |
| --- | --- |
| `composeFile` | The compose file, relative to the repository. |
| `composeProject` | Compose project name of slot 0. Default: `<project name>-teststack`. Slot n appends `-n`. |
| `imageTag` | Tag given to images named through an env variable (see `services.<name>.image`). Default: `<project name>-teststack`. Slot n appends `-n`. |
| `stateDir` | Generated state. Default: `.factory/state/teststack`. |
| `ports.<name>` | `base`: the host port on slot 0. `env`: the variable the compose file publishes it with (`"${WEB_HOST_PORT:-18080}:8080"`). Slot n uses `base + slotStride * n`. |
| `urls.<name>` | URLs for people, tests and agents, with `{port:<name>}` placeholders. `baseUrl` names the one tests start from (default: the first). |
| `env` | Fixed, test-only values written to the stack's env file (passwords). A variable of the same name in the caller's environment wins. |
| `envTemplate` | Optional env file listing every variable the compose file needs. After a build each of them must have a value. |
| `services.<name>` | A compose service whose image is built from the repository. `inputs`: globs (`**` crosses folders), folders ending in `/` or exact paths; a change to a matching file means the image must be rebuilt. `image.env`: the compose file takes the image from this variable (`image: "${WEB_IMAGE}"`); the launcher retags the built image `<name>:<imageTag>` and writes the variable. `image.name`: a fixed image name. Without `image`, the image is compose's own (`<project>-<service>`). |
| `resolver` | Optional module that computes more inputs per service: `pack:<path>` inside a language pack, or a path in the repository. It exports `serviceInputs(service, { name, root, config })` and returns inputs. `pack:dotnet/stack/services.mjs` walks MSBuild project references from `services.<name>.project`. |
| `rebuildAll` | Inputs that affect every image. The compose file always does. |
| `build.all` | Shell command that builds every image. Default: `docker compose build`. |
| `build.service` | Shell command that builds one image; `{service}` is the compose service. Default: `docker compose build <services>`. `build.serviceNext`, when set, is used for the second and later services of one rebuild. |
| `build.env` | Environment of the build and publish commands. |
| `build.envFile` | Env file (or a list of candidates; the file name may contain `*`) that `build.all` writes, with the image names. It becomes the stack's env file. |
| `build.builtTag` | Tag the build gives its images before they are retagged per slot. Default: `latest`. |
| `build.inputs`, `build.exclude` | What `build` hashes to decide whether the images are current. Default: the whole repository. |
| `publish` | Shell command that generates the compose file into `{out}`. Optional. |
| `publishCheck` | Shell command for `publish --check`. Without it, `--check` publishes to a temporary folder and compares each generated file with the committed one. |
| `poolSize`, `maxSlot`, `slotStride`, `leaseTtlSec`, `stackMemoryMb` | Slots: see [Slots](#slots-parallel-stacks). Defaults 2, 8, 1000, 14400 (seconds), 2000. |

Commands may use `{service}`, `{out}`, `{slot}`, `{project}`, `{imageTag}`, `{stateDir}`, `{envFile}`, `{composeFile}` and `{packs}` (the installed language packs, for a pack's build helper such as `node {packs}/dotnet/stack/publish-container.mjs {service}`, which builds .NET images with `dotnet publish -t:PublishContainer` when the services have no Dockerfile). They run from the repository root with the stack's variables (ports, `stack.env`, `build.env`) and `TESTSTACK_SLOT`, `TESTSTACK_PROJECT`, `TESTSTACK_IMAGE_TAG`, `TESTSTACK_STATE_DIR`, `TESTSTACK_ENV_FILE` and `TESTSTACK_COMPOSE_FILE` in the environment. Tools installed per user are found through `project.toolPaths`.

`build` (which `up` runs for you) rebuilds only when the hash of `build.inputs` changed, an image is missing, or another checkout rebuilt this slot's images. Builds are serialized machine-wide through a lock, because a build may tag a shared name before the image is retagged for its slot.

## The `teststack` section

What the stack contains and when it is ready. Defaults are in `scripts/teststack/config.json`.

```json
{
  "teststack": {
    "stores": {
      "db": {
        "type": "postgres",
        "service": "postgres",
        "passwordEnv": "DB_PASSWORD",
        "databases": ["appdb"],
        "preserveTables": ["schema_migrations"],
        "migrationsReady": { "table": "schema_migrations", "column": "version" }
      },
      "cache": { "type": "redis", "service": "redis" },
      "bus": { "type": "rabbitmq", "service": "rabbitmq", "queues": ["orders"] }
    },
    "infrastructureServices": ["postgres", "redis", "rabbitmq"],
    "services": [
      { "name": "api", "url": "http://localhost:{port:api}/healthz", "databases": ["appdb"], "queues": ["orders"] },
      { "name": "web", "url": "http://localhost:{port:web}/" }
    ],
    "restartAfterLoad": [{ "service": "api", "when": "always" }]
  }
}
```

| Key | Meaning |
| --- | --- |
| `scenariosDir`, `baseScenario`, `defaultScenario` | Defaults: `.factory/stack/scenarios`, `_base`, `default`. Set `baseScenario` to `null` to have none. |
| `stores.<name>` | One datastore. `type` picks the adapter; `service` is its compose service (default: the store's name). The store's name is the key scenarios use. |
| `infrastructureServices` | Compose services that must run but are not the application (datastores, proxies). |
| `services` | The application's compose services. `url`: must answer with a status below 500 (`{port:<name>}` placeholders; `"http2": true` for gRPC-only ports). `databases`: databases this service migrates at startup. `queues`: queues it consumes. |
| `restartAfterLoad` | Services that cache state a load invalidates. `{ "service", "when": "always" }` restarts on every load; `"when": "sequencesUsed"` only when a configured sequence (optionally limited by `"sequences": [names]`) handed out a value since the last load. A bare string means `always`. |
| `healAfterSec` | A running service that stays unready this long while the stores are healthy is restarted once. Default 60; 0 disables. |
| `timeoutSec` | Default for `--timeout`. Default 300. |
| `commands` | Extra commands: name to module. |

### Stores

Adapters run the datastore's own command line client inside its container (`docker compose exec -T <service> ...`), so the host needs no client library and no published port.

| Type | Client | Settings |
| --- | --- | --- |
| `postgres` | `psql` | `username` (default `postgres`), `passwordEnv` or `password`, `adminDatabase` (`postgres`), `databases`, `preserveTables`, `migrationsReady`, `sequences`, `onMissingTemplate` |
| `redis` | `redis-cli` | `passwordEnv` or `password`, `database` (0) |
| `rabbitmq` | `rabbitmqctl` | `vhost` (`/`), `queues` (the queues to purge), `user` (`rabbitmq`: the container user the client runs as) |
| `mysql` | `mysql` (`"cli": "mariadb"` on MariaDB images) | `username` (`root`), `passwordEnv` or `password`, `databases`, `preserveTables`, `migrationsReady` |
| `mongodb` | `mongosh` | `username`, `passwordEnv` or `password`, `authDatabase` (`admin`), `databases`, `preserveCollections`, `migrationsReady: { "collection" }` |

`passwordEnv` names a variable of the stack's env file (`stack.env`).

SQL store settings:

- `databases`: names, or `{ "name", "preserveTables", "migrationsReady" }` to override the two per database.
- `preserveTables`: tables a reset never truncates, as `table` or `schema.table`. Put the migration tool's history table here (`schema_migrations`, `flyway_schema_history`, `__EFMigrationsHistory`, `_sqlx_migrations`, `alembic_version`, `django_migrations`).
- `migrationsReady`: how to tell that a database is migrated: `{ "table", "column" }` or `{ "sql": "SELECT ..." }`. The query must return at least one row once the migrations ran. Without it the database only has to exist.
- `sequences` (PostgreSQL): standalone sequences, which no column owns, as `{ "database", "sequence", "table", "column" }`. After a load they are moved to `MAX(column) + 1`. Sequences owned by a serial or identity column are always moved.
- `onMissingTemplate` (PostgreSQL, `--hard`): see [Reset semantics](#reset-semantics).

A custom adapter is a module whose path is the store's `type` (`./.factory/stack/adapters/search.mjs`, or `pack:<path>`). `scripts/teststack/lib/stores/index.mjs` documents the interface: `normalize`, `probe`, and optionally `parseSection`, `count`, `serviceChecks`, `clear`, `load`, `fixups`, `usedSequences`, `restore` and `snapshot`.

### Readiness

The stack is ready when all of the following hold:

- Every container in `infrastructureServices` and `services` is running.
- Every store answers.
- Every service `url` answers below 500.
- Every database passes its `migrationsReady` probe. Databases no service lists are checked too.
- Every queue a service lists exists and has at least one consumer.

`wait` restarts a service once when it stays unready for `healAfterSec` while the stores are healthy. This covers a consumer that fails to connect at startup and never retries.

Choose a `url` that only answers once the service finished starting, migrations included. If the framework starts listening before the migrations ran, rely on `databases` and `migrationsReady` for that part.

### Extra commands

`teststack.commands` maps a command name to a module (`pack:<path>` or a path in the repository) whose default export is `(args, ctx) => result`. `args` is `{ positionals, options }`; the result's fields are printed in the JSON line. The .NET pack ships one: `"hash-password": "pack:dotnet/stack/hash-password.mjs"` prints an ASP.NET Core Identity V3 password hash for scenario rows.

## Reset semantics

**Soft (default).** In order:

1. Wait for readiness (skip with `--no-wait`).
2. Stop the services `restartAfterLoad` names.
3. Purge the queues.
4. Clear every store: truncate every table except `preserveTables` and restart every sequence; flush Redis; empty every collection except `preserveCollections`.
5. Purge the queues again, since services may have published while the stores were cleared.
6. Load the scenario layers, one transaction per database.
7. Run the stores' fix-ups (sequences move past the loaded ids).
8. Start the stopped services and wait for readiness.

A load that fails leaves the stores cleared and the failing database's transaction rolled back.

**Hard (`--hard`).** Use it when a test changed the schema or left state outside tables. It stops the application services, recreates each PostgreSQL database from `<db>__template`, clears the other stores, starts the services, waits, and loads the scenario. `<db>__template` is a snapshot of the migrated, empty schema. It is created on first use and replaced when the `migrationsReady` rows (or, without a probe, the list of columns) differ from the database's. When a database has no usable template, `onMissingTemplate` decides:

- `truncate` (default): truncate the database as it is and snapshot it. Safe for any application, but a schema change a test made before the first snapshot is part of the snapshot.
- `drop`: drop the database, let the application recreate it from its migrations at startup, then truncate and snapshot it. Use it only when the application creates its own database.

MySQL and MongoDB have no snapshots: `--hard` restarts the services and clears those stores like a soft reset.

## Scenario files

Scenarios live in `.factory/stack/scenarios/<name>/scenario.yaml`. `scenario.json` works the same way and needs no YAML parser. You can pass any path instead of a name. YAML files are read with the `yaml` npm package, which the factory install provides.

```yaml
description: Alice has one shipped order and a basket.
extends: default                     # optional; a name, a path, or a list. Applied before this file.
db:                                  # a store from teststack.stores, here of type postgres
  appdb:                             # one of its databases; steps run in order
    - sql: orders.sql                # a raw SQL file, relative to this file
    - table: sales.buyers            # or just the table name for the default schema
      rows:                          # inline rows; or rowsFile: buyers.json|yaml
        - { id: 1, name: Alice, joined: 2024-05-01T10:00:00Z }
cache:                               # a store of type redis
  - key: basket:1
    json: { buyerId: 1, items: [] }  # or value: "raw"; ttl: seconds
```

| Store type | Section |
| --- | --- |
| `postgres`, `mysql` | Database name to a list of steps: `sql: <file>`, or `table` with `rows` or `rowsFile`. |
| `redis` | A list of `key` with `json` or `value`, and an optional `ttl` in seconds. |
| `mongodb` | Database name to a list of steps: `js: <file>` (a mongosh script; `db` is the database), or `collection` with `documents` or `documentsFile`. Documents are MongoDB Extended JSON. |
| `rabbitmq` | None. |

Rules:

- Column names must match the database exactly, including case.
- Columns you leave out get their defaults. Use explicit ids; sequences are fixed up afterwards.
- PostgreSQL rows are inserted with `json_populate_recordset`, so the database converts each value to the column's type. Timestamps, uuids and JSON columns can be written as plain values.
- An unquoted YAML value that looks like a JSON number, `true`, `false` or `null` gets that type. Everything else is a string, including `02134`. Quote values like `"98052"` to keep them strings.
- Numbers pass through JavaScript doubles. Quote a number with more than 15 significant digits.
- SQL files run through `psql` or `mysql`, so lines starting with a client meta-command (`\copy`, `DELIMITER`) are interpreted by the client.
- Unknown keys, stores, databases or files fail with exit code 3 before anything is touched. A step the database rejects fails with exit code 3 and names the step.

To write a new scenario:

1. Copy one from `.factory/stack/scenarios/`.
2. Run `factory teststack validate <name>`.
3. Run `factory teststack load <name>`.

Scenario specs live in `e2e/teststack/`. A spec loads its scenario in `beforeAll` with `loadScenario()` from `e2e/teststack/scenario.ts` and builds its URLs with `port()`, `url()` and `BASE_URL` from `e2e/teststack/ports.ts`, which ask `factory stack info` for the slot in `TESTSTACK_SLOT`. `playwright.teststack.config.ts` runs them in the `scenarios` project, after the other projects.

## Slots (parallel stacks)

Several isolated copies of the stack can run on one machine, for example one per agent worktree. Each copy is a **slot**:

| | Slot 0 (default) | Slot n (1..`maxSlot`) |
| --- | --- | --- |
| Select | nothing, or `--slot 0` | `factory teststack --slot <n> <command>` or `TESTSTACK_SLOT=<n>` |
| Compose project | `<project>-teststack` | `<project>-teststack-<n>` |
| Host ports | `stack.ports.<name>.base` | every base + `slotStride` × n |
| State | `.factory/state/teststack/` | `.factory/state/teststack/slot-<n>/` |
| Image tags | `<imageTag>`, or compose's `<project>-<service>` | the same with `-<n>` |
| URLs | `stack.urls` with slot 0's ports | the same, on the slot's ports |

For this to work the compose file must publish every host port, and every URL the browser sees, through the variables named in `stack.ports` (`"${WEB_HOST_PORT:-18080}:8080"`). The launcher writes the slot's values into the slot's env file.

**Leasing.** Slot 0 is reserved for people. Agents lease slots 1..`poolSize` (default 2, overridden by `TESTSTACK_SLOTS`):

```bash
factory stack lease --owner implement:SHOP-3 --wait-sec 600 [--pid <owner pid>]
# {"ok":true,"command":"lease","owner":"implement:SHOP-3","slot":1,"project":"shop-teststack-1",
#  "baseUrl":"http://localhost:19080","urls":{...},"webUrl":"http://localhost:19080","ports":{"web":19080,...},...}
factory teststack --slot 1 up --scenario default
TESTSTACK_SLOT=1 npx playwright test -c playwright.teststack.config.ts ...
factory teststack --slot 1 down
factory stack release --slot 1 --owner implement:SHOP-3
factory stack list            # every pool slot, its owner and whether the lease is stale
factory stack info --slot 1   # project, state paths, image tag, ports and URLs of a slot
```

- When no slot is free, `lease` polls until `--wait-sec` runs out, then prints `{"ok":false,...}` and exits 2.
- Leases live in `~/.ai-app-factory/teststack/<project>/leases/`, because they are taken from different worktrees and ports are machine-wide. Claims are serialized by an atomic `mkdir` mutex and each lease file is created with `O_EXCL`.
- A lease is stale, and the next `lease` takes it over, when its owner pid is gone or it is older than `leaseTtlSec` since it was taken or last renewed (`factory stack renew --slot <n>`). The owner pid defaults to the parent process of the CLI; pass `--pid` when that is a short-lived shell.
- `release` does not stop the stack. Run `down` first unless the next owner should reuse it.
- `lease` warns (stderr and `warning`) when Docker's memory looks too small for one more stack of `stackMemoryMb`.
- Other scripts can import everything from `scripts/stack/lib/index.mjs` (`lease`, `release`, `renew`, `listLeases`, `slotInfo`, `slotPorts`, `servicesFor`, ...).

**Incremental rebuilds.** After code changes in a worktree, rebuild only what changed:

```bash
factory teststack --slot 1 rebuild-changed --base main
# {"ok":true,"command":"rebuild-changed","base":"main","changedFiles":7,"services":["api","web"],"full":false,
#  "recreated":["api","web"],"wait":{...},"elapsedMs":41000,"slot":1,...}
factory teststack services-for shared/contracts/orders.proto   # -> the services whose inputs match
```

Each affected image is built with `stack.build.service`, then only those containers are recreated (`compose up -d --no-deps`). `rebuild-changed` builds everything (`"full":true`) instead when the slot's images were not built from this checkout (another worktree used the slot since) or when every service is affected anyway. A rebuild trusts the diff: a change that was made and then reverted after the last build is not seen, so run `build --force` if in doubt.

## Agent workflow

```bash
factory teststack up --scenario order-history || exit $?   # first run builds the images; later runs reuse them
# ...run tests, or probe the URLs in the JSON result...
factory teststack load default                             # reset between tests
factory teststack status                                   # JSON readiness report when something looks wrong
factory teststack logs api
```

On macOS without Docker Desktop, [colima](https://github.com/abiosoft/colima) works: `brew install colima docker docker-compose`, then `colima start --cpu 8 --memory 16 --vm-type vz --mount-type virtiofs`.

## Tests

`node --test scripts/stack/test/*.test.mjs scripts/teststack/test/*.test.mjs` runs without Docker: the store adapters are tested with a fake command runner that records the commands and scripts they would run.
