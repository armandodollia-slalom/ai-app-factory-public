# Implement stage: settings and records

**Who reads this:** C (operators) looking up a flag, a setting, a limit or a record of the
[implement stage](implement.md). Read [implement.md](implement.md) first for what the stage does.

## Command options

| Option | Meaning |
| --- | --- |
| `--dry-run` | Print the order, branches and bases, then stop. No agents run. |
| `--parallel N\|auto` | Run up to N stories (or bug groups) at once. `auto` (the default, `implement.maxParallel`) sizes it from free memory; see [Resources](implement.md#resources). Each has its own worktree; dependents still wait for their blockers. |
| `--base <ref>` | Base for stories with no in-batch blocker (default `baseRef`, `origin/main`; fetched first). |
| `--pr` | Deliver each finished branch: push it and open its PR through the code host, against its base branch (stacked PRs for dependents), as [The PR opens finished](implement.md#the-pr-opens-finished) describes. On GitHub the push and the PR are made as your [PR bot](setup.md#the-pipelines-pr-bot) `dev-bot-<gh login>`, so you can approve the PR yourself; until `factory bot setup` has run, the run warns and uses your own `gh` login. A bug-fix PR then goes through the [review gate](review-gate.md). |
| `--epic <EPIC>` | Implement every story and bug of the epic (its child tickets on the board, fetched into the ticket cache), in Blocked-by order, in addition to any given. The epic's own ticket folder (its body and mockups) is handed to the agents too, and copied into every worktree of the run. |
| `--delivery epic\|story` | How an epic is delivered (`implement.delivery`, default `epic`): one epic branch and one PR (bug epics: one PR per group of bugs), or a branch and PR per story. See [Delivery modes](implement.md#delivery-modes). |
| `--grouping auto\|epic\|ticket` | Bug epics (`implement.epic.grouping`, default `auto`): `auto` lets the orchestrator group the bugs into PRs when most tickets are bugs, `epic` forces one PR, `ticket` one PR per bug. See [How an epic is split into PRs](implement.md#how-an-epic-is-split-into-prs); `--grouping` wins over `--pr-split`. |
| `--pr-split epic\|story\|groups` | Feature epics (`implement.epic.prSplit`, default `epic`): one PR for the epic, one PR per story, or PR groups the orchestrator chooses (at most `implement.epic.maxTicketsPerGroup` stories each). See [How an epic is split into PRs](implement.md#how-an-epic-is-split-into-prs). Proven by fixture tests only for `story` and `groups` ([proof](../../README.md#what-has-been-proven)). |
| `--standalone` | A ticket of an epic whose epic run is in progress gets its own branch and PR instead of joining the epic's branch. A ticket of a delivered bug group whose PR is still open, reopened by a person, joins that group again whatever this says ([Delivery modes](implement.md#delivery-modes)). |
| `--force` | Also implement stories already implemented (their issue is closed, or this checkout's run record delivered them), and run stories whose [board](board.md) card is already in Pending Review or Done. |
| `--takeover` | Take over board cards another machine holds in In Progress or Testing (otherwise those stories, and stories stacked on them, are skipped). |

## Limits

| Limit | Default | What happens when it is reached |
| --- | --- | --- |
| `maxSubtasks` | 4 | Plan rejected: split the story |
| `maxConcurrentPairs` | 2 | Further subtasks wait (per story) |
| `maxConcurrentAgents` | 6 | Agent runs wait for a slot (machine-wide, across stories) |
| `maxCouncilRounds` | 3 | The pair escalates to the orchestrator (the pair's council passes at `councilPassScore`, 9.5) |
| `maxTakeovers` | 1 | A second takeover is refused; the subtask fails |
| `maxAgentRunsPerStory` | 20 | Story ends `limit-agent-runs` (every harness-run agent counts, including the orchestrator's integration and fix runs; review and feature verification agents are their stages' own) |
| `storyWallClockSec` | 10800 | The usual budget; the story ends `limit-wall-clock` only at `agent.supervisor.ceilingFactor` (10) times it; agent limits are clipped to the time left |
| `timeoutsSec.planner`, `orchestrator`, `pairImplementer`, `pairVerifier`, `pairUiVerifier`, `checks` | 1800, 3600, 1800, 600, 1200, 1800 | Per run: an agent is stopped when it makes no progress for `agent.supervisor.idleSec` (1800) or at `ceilingFactor` times its limit ([Slow agents](implement.md#slow-agents-never-change-an-outcome)) |

Hard stops are recorded (`limit_hit` in `implement-runs.jsonl`, `limitHit` in the decision log).

## Config

The defaults are the engine's (`scripts/implement/config.json` on top of `scripts/pipeline/config.json` in the factory install). A repository overrides any of them in its `.factory/config.json`, under the same keys ([configuration](../configuration.md)). The engine ships no build or test command: `prepareCmd`, `checks`, `unitTests.cmd` and `ui.teststackCmd` have no default, `factory init` drafts the first three from the language packs, and the [`onboard-codebase`](../../skills/onboard-codebase/SKILL.md) skill corrects them.

Every setting of the `implement`, `prCheck` and `resources` sections, with what it does, its allowed values, its default and the environment variable that overrides it, is in the [settings reference](../configuration.md#settings-reference). What the reference cannot say in a row:

- `implement.worktreeDir`: `{repo}` is the checkout's folder name; subtask worktrees sit next to their ticket's, as `<key>--<id>`.
- `implement.maxParallel`: an upper limit on the number of tickets worked out from free memory ([Resources](implement.md#resources)); `--parallel N` forces N.
- `prCheck.mode`, `prCheck.fixMinSeverity`, `prCheck.bugFixMinSeverity`, `prCheck.fixLenses`: the PR check before a ticket's or an epic's PR opens: [fix mode](pr-check.md) (`report` keeps the report round's verdict, `off` runs none) and the [returns to implementation](pr-check.md#findings-about-the-production-change-go-back-to-implementation) (`prCheck.returnToImplementation.*`).
- `implement.epic.*`: [Epic delivery](implement.md#epic-delivery); `prSplit` ([How an epic is split into PRs](implement.md#how-an-epic-is-split-into-prs)) and `maxTicketsPerGroup`, one cap for bug groups and feature groups.
- `implement.reviewGate.*` and `implement.autoMerge.*`: the [review gate](review-gate.md) and [auto-merge](review-gate.md#auto-merge) of Low bug-fix PRs.
- `implement.waitSec.*`, `implement.pollSec.featureVerification`: the usual time feature verification and the Stop hook's PR check take at most; the run waits while they are alive (a dead run is resumed) and gives up only at `agent.supervisor.ceilingFactor` times it. A PR check that did not complete ends the ticket `pr-check-incomplete`: the branch is pushed, no PR opens.
- `implement.ci.parity.enabled`: `false` skips the [CI parity run](ci-parity.md) of a single ticket and of a feature epic's PRs (a bug group's parity run still runs) and, for every delivery, the pre-push [analysis gate](analysis.md#ci).
- `implement.ci.maxFixRounds`: one count of every CI fixing round of a ticket, before its PR opens and after it while the PR is held; `0` sends a red head to a person.
- `implement.ci.wait.enabled`: `false` makes no CI proof before the open and no wait after it; the PR opens ready and its body says CI was not proven.
- `implement.preOpen.*`: [After the open](implement.md#after-the-open). The order itself is not a setting: the keys this section used to have stop the settings from loading ([configuration](../configuration.md)).
- `implement.worker.*`: a ticket whose worker failed (`error`, `fv-not-started`) is retried in its worktree; the wait doubles each retry.
- `implement.subtaskModels`: the `models.pool` entries the planner may give a subtask's pair implementer (`null`: every entry); it names one per subtask in `model`, and a plan naming another is refused. The orchestrator runs on `implement.orchestrator.model` (else `orchestrator.model`) and the pair verifiers on their own entries (`models.agents.pair-verifier`, `pair-ui-verifier`); every entry a plan needs is resolved when the plan is accepted ([models](models.md)), so a missing entry fails the plan, not a pair.
- `implement.checks`: `[{ "name", "cmd" }]`, for example `{ "name": "build", "cmd": "cargo build --workspace" }`; verifiers get their output and a failure fails the round.
- `implement.unitTests.cmd`: runs for each service of `project.services` with changed files (by its `paths`) that declares `unitTests`, and for every service that lists such a service in `dependsOn`. A `unitTests` value with a space in it is a whole command; a path that does not exist in the worktree is skipped.
- `implement.uiStory.*`: what makes a story a UI story ([Plan](implement.md#plan)); the files that do are `project.frontendPaths` plus the frontend services' paths.
- `implement.ui.*`: the stack slot contract and timing ([UI verification](implement.md#ui-verification)); a relative script path in `slotsCmd` is looked up in the engine's install first, one in `teststackCmd` in the worktree.
- `lsp.client.*`: [Language servers](implement.md#language-servers); relative script paths are looked up in the engine's install first, then in the repository.
- `implement.decisions.*`: labeling thresholds ([Decision log](#decision-log)).

Each agent's CLI is its pool entry's ([models](models.md)). Every harness agent runs with subagents disabled (Claude's `Agent` and `Task` tools); pair implementers get the implement-mode deny list (no push, reset, checkout, switch, rebase, worktree); verifiers are read mode, the UI verifier verify mode (shell but no file edits or git writes; the harness also discards whatever a verifier leaves in the worktree). Parallel stories each run their own orchestrator, pairs, reviewer and feature verification agents, so `--parallel` multiplies LLM usage; `maxConcurrentAgents` caps the total. Implementers are told never to use the shared test stack (`factory teststack up` or `load`); UI verification uses leased slots instead.

## Decision log

The orchestrator's decisions go to the pipeline's shared decision log, `.factory/metrics/decisions.jsonl` (`scripts/pipeline/lib/decisions.mjs`), where every stage records why its agents decided what they did and which the [retro](retro.md) reads (section `implement` of its digest). Their outcomes are metrics in two more files. All are append-only in `.factory/metrics/` (committed with the story, `merge=union`) and join on `decisionId` (one UUID per accepted plan, `decision_id` in `decisions.jsonl`) and `subtaskId`. A separate decisions file is not needed: the shared log's records take any extra structured fields, so a plan's reasons and expectations fit in it as they are.

| File | One record per | Fields |
| --- | --- | --- |
| `decisions.jsonl`, stage `implement-plan` | plan attempt (decision `plan-written`, `plan-rejected` or `blocked`) and escalation (`escalation-rewrite`, `escalation-takeover`, `gave-up`) | the shared fields (`ts`, `stage`, `story`, `round` = attempt, `agent`, `agent_ver`, `subject`, `decision`, `reason`), plus for plans `decision_id` (null when rejected), `mode`, `mode_reason`, `split_reason`, `rejection_reasons`, `orchestrator` {`cli`, `model`}, `features` {`services`, `acceptanceCriteria`, `uiStory`, `estimatedSize`} and `items` = the subtasks [{`id`, `goal`, `owns`, `dependsOn`, `model` (the pool entry the pair implementer runs on), `modelReason`, `verify`, `verifyReason`, `expectedFiles`, `expectedLoc`, `confidence`, `alternatives`}]; for escalations `decision_id`, `subtask`, `pair_outcome` and the findings that led to it |
| `decisions.jsonl`, stage `bug-triage` | published bug-fix PR ([review gate](review-gate.md#where-it-is-recorded)) | the PR's severity, class, systems and gate decision, and per ticket in `items` the ratings, severity (base, bump, floor), confidence and reopens |
| `decisions.jsonl`, stage `implement-verify` | pair round with a verdict | `agent` (`pair-verifier` or `pair-ui-verifier`), `subject: pair-implementer`, `decision` (`approved`, `changes-requested`), `reason`, `decision_id`, `subtask`, `design_findings` (count of `category: "design"` findings), `items` = the findings (the verifier's and the harness's own scope, build and diagnostics findings) with `severity`, `category`, `file`, `line`, `screenshot`, `reason`, `fix`, and for design findings `mockup` and `actual` |
| `subtask-runs.jsonl` | subtask, when it ends (after its merge) | `decisionId`, `subtaskId`, `implementer` and `verifier` {`cli`, `model` (the pool entry), `promptVersion`}, `model` and `effort` (the pair implementer's pool entry), `verify`, `maxRounds`, `rounds` [{`round`, `verdict`, `findings` (counts by `severity/category`), `designFindings`, `diagnostics` {`errors`, `warnings`}, `outOfOwnsEdits`, `crossSubtaskFindings`}], `designFindings` (the rounds' sum), `approved`, `escalation` (`none`, `rewrite`, `takeover`), `filesNeededOutsideOwns`, `mergeConflictFiles`, `expected` and `actual` {`files`, `loc`}, `tokens`, `cost` (USD) and `premiumRequests`, summed from the subtask's agent runs ([costs](costs.md)), `wallClockSec`, `agentRuns`, `leaseWaitSec`, `lspCalls`, `signatureChangesWithoutReferences` |
| `decision-outcomes.jsonl` | event | `type: "escaped"`: a story-level review finding or a file changed by a feature verification bug fix, credited to the subtask whose `owns` matches (`subtaskId` null when none does), with `source` (`arch-review`, `feature-verification`) and the findings/files. `type: "story"`: the story's `outcome`, `reason`, `tokens`, `cost`, `premiumRequests` (every agent run of the orchestrated flow), `wallClockSec`, `agentRuns`, `reviewBlocks`, `bugFixCycles`, `limitHit`, `lspCalls`, `signatureChangesWithoutReferences`. `type: "late"` (written by `board sync` when the card reaches Done, in the main checkout, uncommitted): `prMerged`, `humanCommits` and `humanLines` (PR commits not reachable from the head the pipeline finished on), `humanAuthors`, `bugStories` (`BUG-*` tickets that name the key), `reverts` (null: a hook for a later revert detector). The [review gate](review-gate.md) adds, in the main checkout (uncommitted, like `late`): `type: "reopen"` (a human reopen of a triaged bug fix: `story`, `pr`, `source`, `by`, `afterMerge`, `reopens`, `severity`), `type: "pr-review"` (a gated PR closed: its class features, how people reviewed it, the outcome known then) and `type: "revert"` (a gated PR's merge reverted on the base) |

`implement decisions [--story KEY] [--json]` joins them and labels each subtask (thresholds in `implement.decisions`). Its **Design e/pr** column sets the design findings the UI verifiers caught early (the subtask's `designFindings`) against the design findings the [PR check](pr-check.md) upheld later for the story (`.factory/metrics/pr-checks.jsonl`, each finding id once per check; an epic check credits a finding to the ticket its requirement names, else to every ticket it covered), and the report ends with both totals. In `--json` they are `designFindings` and `prCheckDesignFindings`. A falling PR-check count with a steady early count means the design is caught while it is cheap to fix.

| Label | Rule |
| --- | --- |
| `over-provisioned` | The pair implementer's pool entry above `low` effort, approved in round 1 with no escalation, actual LOC ≤ `smallDiffLoc` (60) |
| `under-provisioned` | Escalated, used every round, or not approved |
| `bad-split` | Merge conflicts, edits or needs outside `owns`, or findings pointing at another subtask's files |
| `should-have-been-self` | (per plan) Delegated, every subtask ≤ `tinySubtaskLoc` (40) LOC and ≤ `tinySubtaskFiles` (3) files, total ≤ `selfMaxTotalLoc` (150), and more than `selfOverheadRunsPerSubtask` (2) agent runs per subtask |
| `weak-verification` | An escaped defect was credited to the subtask |
| `bad-grouping` | (per bug PR group) Some of the group's tickets verified and others did not, or merging its tickets conflicted ([epic split](implement.md#how-an-epic-is-split-into-prs)) |

Caveats: compare decisions only between stories with similar `features` (services, acceptance criteria, size); a bigger story legitimately needs more rounds. A change to a verifier's prompt (its `promptVersion`) changes how strict it is, so round counts and escaped defects before and after are not comparable. LOC expectations are the planner's guesses; the useful signal is the trend of expected versus actual, not single misses.

## Delivery records

**CI cost.** The pipelines are not run twice for the same head. In the generated GitHub Actions workflows, a PR event's run of the gate and analysis workflows starts with a `reuse` job: it finds the same workflow's push run on the same head, every job of it successful, with the base not ahead of the head, and then the other jobs stand down. Otherwise, or when that check fails, they run in full. Nothing counts as green for having been skipped: the PR run's verdict is the reuse job's verified success, and the push run whose jobs carry the required check names passed on the same SHA. The `reuse` job is never a check the host requires (`review-gate enforce` leaves it out): the workflow's own jobs carry the required names. Other CI systems run their branch pipelines by their own rules and repeat them on the PR.

**The audit.** Every delivered PR's run record has `readyAt`, its holds (`[{ mode, label, ok, from, to, why, error?, cycle?, releaseConfirmed?, releaseFailedAt? }]`) and `readyAudit`: the agent runs of the story (token-usage rows: start = end − seconds) that started after the PR was ready, outside every confirmed hold (holds with `ok: false` are ignored, and only confirmed ones count toward `implement.ci.maxFixRounds`). A draft-first PR whose draft was not confirmed records it as `{ mode: 'draft', ok: false }` before its label hold; on green every hold without `to` gets `to` and `releaseConfirmed: true`. `hold-failed` and `release-unconfirmed` keep `phase: ci-wait` with `holdFailed` or `releaseConfirmed: false` (an epic unit record gains `holdFailed`); `gate-assessment-failed` keeps `phase: pre-open` and `greenAt`; a story planned under `--dry-run` carries `prUnchecked`. `factory doctor` fails when any delivered PR has an agent run after ready, and `run-conditions.jsonl` gets a `pre-open` row per delivery: first push, open and ready times, branch CI pipelines and rounds, holds, agents after ready, and `hold_failed` or `release_confirmed: false` when they apply.

**Expected checks per head.** A head owes the pipelines of the events that happened to it. Before the PR: a push of the branch. On the PR: the activities the pipeline recorded for that head in its head ledger (`opened`, `synchronize`, `ready_for_review`, `labeled`, `reopened`); a head the pipeline did not push is a `synchronize`. A PR the pipeline did not open owes every pipeline of `opened`, `synchronize` and `reopened` (fail closed). A newer skipped run never supersedes a run that executed ([review-gate.md](review-gate.md)).

## A host that refuses the PR's text

A content filter can refuse a pull request for a few words of its body (GitHub has answered a bare HTTP 403 after a 60 s hang for the text `StringLength(100, Min 6)` in the "Behaviour changes" section, while a 26 KB body without it was accepted). Every host adapter classes a refusal of the text (`HostRefusedError`, code `refused`: a 4xx naming spam or content, or a 403 with no reason, on a call that sends text) apart from a permission error (a 403 that names a scope, token or permission) and a rate limit; only the first is retried. The open is sent again with the body reduced in a fixed, deterministic order (`scripts/pipeline/lib/hosts/refusal.mjs`): the demo video, the API summary, the council tables, the static analysis, any other section from the end back, then the follow-ups and the behaviour changes outside the ticket, then the run details; the summary, the review and test lines and the CI and gate evidence lines are never dropped; last, the title is shortened to the ticket key. No agent starts for the reduction, so the PR still opens finished. The accepted body says which sections were left out and why; the full body and every attempt are kept in `.factory/state/pr-open/<branch>.{md,json}`, and the left-out sections are posted as comments, each on its own (one the host refuses too is recorded as refused). `run-conditions.jsonl` gets a `host-refusal` row. Refused even when shortest, the delivery ends `pr-refused`: the run record stays at `pre-open` with `greenAt`, the head and the refusal, and the next `implement run` or `implement resume` delivers again from the saved title and body (`pr-check/<KEY>-delivery-input.json`). That resume calls the delivery steps again (the analysis jobs and the branch CI proof; what they reuse for an unchanged head is theirs), a bug fix reuses a gate rating saved for that very head, and the demo video step runs again unless that commit's finished step stored its media, so the narrator can run; it continues only while the branch is at the head CI proved; see [Resume](implement.md#resume-and-interrupted-runs). The tracker contract does the same for ticket and comment creation (`withRefusalFallback` in `scripts/board/lib/trackers/index.mjs`, every tracker adapter): a ticket's sections are dropped from the end back and follow as comments; the board's local ticket file keeps the full text.
